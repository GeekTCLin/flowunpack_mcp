# 重构说明（legacy → flowunpack）

本文记录本仓库从 `legacy/` 旧脚本重构为 `flowunpack` 包时的改动，属于开发历史，
不属于使用文档（使用说明见 [`README.md`](../README.md)）。

## 一、修复的硬性缺陷

| 问题 | 原状 | 现在 |
|------|------|------|
| `varint_utils.py` 无法导入 | 用了 `Tuple/List/Dict` 却没 import，直接 `NameError` | 统一到 `codecs.py`，零缺失 import |
| `parallel_unpack.py` 无法编译 | 623 行 f-string 语法错误 | 已废弃，能力并入 `segmentation.py` |
| varint 解码错误 | `shift` 从未递增，`[0x80,0x01]` 解成 1 而非 128 | 修正为 LEB128，并补 `varint_be`/`sleb128`/`zigzag` |
| 三份重复的 varint 实现 | `heuristic_unpack.py`、`varint_utils.py`、`parallel_unpack.py` 各一份且行为矛盾 | 唯一实现 `codecs.py`，全项目复用 |
| 正反向流串味 | 每个包同时写进正向流和反向流，统计被污染 | 按五元组单向分组（`pcap.py`） |
| 误报严重 | 只靠"能走完"判定 | 增加置换检验等三重门槛，随机数据 0 误报 |
| 硬依赖 scapy | 导入即崩 | 核心库**零依赖**；scapy 降为可选（仅读本地 pcap 用） |

## 二、结构变化

旧脚本是若干彼此复制的单文件，没有包边界、没有测试、阈值散落在函数体内。
现在按职责分层：

```
codecs / io_utils      基础层：编解码与输入归一化
models / config        数据模型与全部可调阈值
segmentation / detectors / fields   算法层：分帧 → 多模板 → 字段解释
analyzers              统计层：长度字段评分、结构画像
engine / report        编排与输出
flowunpack_mcp         服务层：MCP 工具
```

## 三、遗留说明

`legacy/` 目录仅作对照保留，不参与构建、不被测试覆盖、不再维护。
需要旧行为时请自行移植，不要直接 import。

## 四、P2 开发记录

按路线图第 8~10 项推进，记录实现中发现的问题与结论。

### P2-9 性能优化（分阶段搜索）

把 `segmentation._search` 拆成"枚举（`_collect_successes`）+ 排序（`_rank_successes`）"
两步，于是可以按子空间**分批**枚举再统一排序 —— 一致性证据（同族假设数）
因此不会被拆散。核心子空间（`stage1_scales × stage1_formats`）的证据已足够强时
直接短路，否则**补搜**剩余子空间；补搜不重复已搜过的部分，因此最坏情况与全量搜索同价。

短路判据必须与最终决策用**同一条**候选级证据（`matched_gap ≥ min_matched_gap`），
否则就是"悄悄换了结论换来的加速"。标定（`bench/calibrate_staged.py`）显示
负样本阶段一首位的 gap 上界 0.119，正样本下界 0.4，取 0.25 有足够余量。

一个反直觉的发现：8 帧 varint 样本上，**全量搜索反而拒绝、分阶段搜索接受**。
原因是排序后取 top-K 做置换检验时，全量搜索的 top-K 被"冷子空间里的伪解"挤占，
真解不在其中；分阶段搜索的阶段一只有核心子空间，真解自然排进 top-K。
结论是分阶段搜索在这类样本上**更准**，因此 `tests/test_staged_search.py` 的
等价性断言写成"分阶段 ≥ 全量"而非严格相等。

### P2-8 双向流联合推断

实现三条耦合证据（结构可迁移 / 类型双射 / 字段身份一致 / 长度相关）时，
按最初的设想"一半未检出、另一半迁移补上"去构造样本，**始终构造不出来**：
`analyze_stream(hint=...)` 要求走查完整且帧数 ≥ `min_frames`，而自身搜索对候选
也要求同一条件，于是"自身检不出、迁移却能走通"几乎不可达。

真正的可达场景是**冲突裁决**：接收侧被一个**自信的伪解**锁定。
响应侧帧长恒定时，长度字段取值跨帧恒定，块置换检验打乱块顺序**不会改变**这些
字节，伪解与真解在置换检验下不可区分；stage-1 短路一旦先撞上伪解就收工，
给出 5 帧 / 匹配 gap 0.74 的错误结论（真解 10 帧）。跨方向的可证伪性
（"A 能解释 B、B 解释不了 A"）是唯一能纠正它的手段。

据此把迁移的触发条件从"接收侧完全未检出"放宽为三种情形（补全 / 裁决 / 互证），
并新增 `Coupling.repaired` 与 `Coupling.conflicts` 两个可观测字段。

过程中踩到并修正的一处过度修正：冲突判据最初用了含 `overhead` 的完整公式签名，
于是"响应包头比请求长 2 字节"这种**常态**被当成冲突，联合置信度被无端打九折
（0.870 → 0.783）。改为只用不含 `overhead` 的长度字段身份签名后恢复。
结论：`overhead` 差异是正常协议形态，不能作为"两侧结论矛盾"的证据。

### P2-10 状态机推断

目标是在消息类型聚类之后回答"消息按什么顺序出现"。方法取 **PTA + k-Tail 状态合并**
（Biermann & Feldman 1972；Netzob 的状态机推断同族），落成 `statemachine.py`。

**为什么不能只用 PTA。** PTA（前缀树接受器）在多条 trace 上才有意义；本项目的输入是
**一条**流，PTA 退化成一条链 —— 零压缩、零信息。真正产生结构的是 k-Tail 状态合并：
两个位置若"后 k 步的符号串"相同则视为同一状态（Nerode 等价的 k 阶近似）。

**实现中撞到的三个坑，都写进了代码注释与测试：**

1. **末尾短窗口必须按最长可用前缀归入已有等价类。** 否则链尾会因为 tail 被截断而与
   任何位置都不等价，凭空多出一个状态，并且它的**前驱**会同时指向两个状态 —— 制造出
   假的非确定性。实测 `[1,2,3]*4` 在 k=2 下冲突数从 0 变成 1。修好后 `ktail_states`
   在三种周期序列上冲突数恒为 0（`test_tail_is_merged_into_prefix_class` 锁死这点）。

2. **"存在回路"不等于"被反复执行"。** SCC 只能找出回路；一条 24 个随机命令字的序列
   也能凑出一个 3 状态环，但环上三条转移各只观测到 1 次 —— 只走过一遍，是巧合。
   因此增加绕行次数门槛（环上各转移观测次数的最小值 ≥ `sm_min_cycle_traversals`）。
   加门槛后该样本的环列表清空、结构强度从 0.12 降到 0.05，而真正的周期样本不受影响。
   这是本次实现里唯一一处"发现诊断输出不对、回头改判据"的修正。

3. **符号互不重复时没有可合并的状态。** 递增序号 / 随机数字段会给出 n 种符号、
   n 个状态、零压缩 —— 那不是推断，是把输入换了个说法。因此加
   `sm_min_symbol_repeats`（符号平均重复次数 ≥ 2）门槛，不达标直接拒绝。

**一个意外的设计收益：符号化回退路径是真实需要的。** 最初以为"keyword 字段"总是
可用，但实际协议里握手命令字常常**只出现一次**，凑不满 `cluster_min_group=2`
的每簇下限，于是 `infer_message_types` 返回单一类型。若只依赖 keyword，几乎所有
"握手 + 循环"的真实形态都会符号化失败。回退到"包头里 cardinality 最小的枚举字段"
之后，`make_interaction_stream` 这类样本（握手 0 + 循环 1,2,3）能正确推断出
4 状态、环长 3、握手只从初始状态出去。诊断与测试因此**刻意覆盖两条路径**
（`keyword@2+1` 与 `field@2+1`）。

**诚实边界（写进 README §5.5 / §11，也在 `StateMachine` 的 docstring 里）：**

- 只从正样本学习 → 状态全为接受态，得到**过近似**自动机，不能判定序列非法。
- 单条 trace **无法唯一确定 k**，也无法唯一确定状态机。因此不假装有唯一答案，
  而是把 `k_sensitivity`（k=1..4 各自的状态数）与 `conflicts` 一并交付。
  实测带单点噪声的样本给出 `{1:4, 2:5, 3:6, 4:7}`。
- `compression = 1 − 状态数/符号数` 是"有没有结构"的**客观度量**，接近 0 时只给
  低置信度并在 `notes` 里写明"推断结果不具解释力"。
- 符号取不到（单符号 / 样本 < `sm_min_symbols` / 重复次数不足）时返回 `None`，
  原因写进 `statistics["state_machine_summary"]` —— **不给结论比给错结论好**。

诊断：`bench/diag_statemachine.py`（周期 2/3/4、握手、噪声、随机、两条符号化路径、
三类拒绝，共 27 项断言）；回归：`tests/test_statemachine.py`（44 项）。

### 零填充包头的超量伪解（2026-09-21 修复）

**症状**：一个 16 字节包头、长度字段在 offset 12 的协议，包头中间的 9 字节保留
字段填 `0x00`（真实协议的常态）时，被判成 `offset=2 uint16_le overhead=5` 的
**30 帧伪解**（置信度 0.83），而真解（10 帧）**根本不在候选列表里**；同样的布局
填 `0xAA` 则完全正确。

**根因**：`segmentation.walk` 当时只要求帧容纳"长度字段 + 1 字节"
（`frame_len >= offset + width + 1`）。当长度字段埋在帧头中间
（`offset + width < overhead`）时，这条判据允许 `frame_len == overhead` 的
**零载荷帧** —— 等价于 `scale * value == 0`，即"长度字段声明了 0 字节载荷"。
零填充让这件事极易发生：零区里任意偏移读出的值都是 0，一条"帧长 = 帧头长"
的假链于是能把整条流等分成 30 段。实测那 30 帧里恰有 10 帧是零载荷帧。

**修复**：`walk` 的帧长下限改为必须容纳**整个帧头**再加 1 字节载荷
（`frame_len > max(overhead + extra, offset + width)`），等价于"长度值不得为 0"。
这是长度前缀协议的结构性必要条件而非调参：真实协议不可能声明 0 字节载荷。
修复后 30 帧伪解全部消失，两个零填充样本都给出正确的 10 帧 + `overhead=16`，
帧边界与金标准逐帧一致；benchmark 33/33、负样本 0/9 误报、210 项断言全绿。
顺带改善：`offset=40` 且放宽到 `max_offset=64, max_overhead=128` 时，
原先退化成 6 帧伪解，现在正确切出 10 帧。

**残留（信息论歧义，非缺陷）**：零填充让长度字段的高/低位字节变成常量，
`(offset, width)` 不可判 —— `uint16_be@12` / `uint8@13` / `uint32_be@10`
读出同一数值、给出同一套帧边界，实测报 `uint32_be@10`。
**试过**把"字段覆盖的恒定字节数"插进 `_dedup_key`（组内选代表）的宽度之前来纠正，
结果 20 项既有断言从 `uint16_be@N` 翻成 `uint8@N+1`、个别样本反而退化 ——
因为它对所有样本都生效，而不只对零填充生效；收益不抵风险，已回退。
最终列入 README §11 的"已知歧义"，测试只断言"字段覆盖了真实长度字节 + 帧头长度正确"。

诊断：`bench/diag_zero_fill.py`（历史伪解复现 / 修复验证 / 等价族 / 填充对照）；
`bench/diag_header_body.py` 与 `diag_header_body2.py` 的判据同步改为
"帧头长度 + 帧数"（不再要求具体 offset）。回归用例：
`test_zero_filled_header`、`test_frame_must_hold_whole_header`。
